# HackSync Phase 6: Benchmarking Engine Guide

## 1. Benchmarking Philosophy

HackSync's benchmark engine evaluates system performance against realistic, curated software engineering tasks. Benchmarks must be:
1. **Deterministic where possible**: AST parsing, security rule matching, patch application, and test discovery must yield identical results across identical runs.
2. **Independent & Non-Circular**: The ground truth for every case is specified independently by humans, never generated by the tool being tested.
3. **Safe to Execute**: Evaluation runs operate with read-only access to code repositories and never perform unapproved mutations.
4. **Transparent**: Every benchmark case reports granular metrics, evaluation methodology, and actionable failure diagnostics.

---

## 2. Benchmark Categories & Taxonomies

Phase 6 supports 10 distinct benchmark categories:

| Category | Description | Primary Evaluator | Key Metrics |
| :--- | :--- | :--- | :--- |
| `project_intelligence` | AST symbol resolution, dependency mapping, framework detection | ProjectIntelligenceEvaluator | Accuracy, Symbol Recall |
| `retrieval` | Symbol and code retrieval across project files | RetrievalEvaluator | Hit@1, Hit@3, Hit@5, MRR |
| `debugging` | Root cause analysis and stack trace diagnosis | AnswerEvaluator | Groundedness, Unsupported Claims |
| `security` | SQL injection, XSS, command injection, path traversal, secrets | SecurityEvaluator | Precision, Recall, F1 |
| `git_intelligence` | Diff parsing, changed symbols, impact radius | GitEvaluator | Changed Symbols Recall, Blast Radius |
| `testing` | Test discovery, runner detection, targeted test execution | TestingEvaluator | Discovery Accuracy, Framework Hit |
| `fixing` | Unified diff generation, patch validation, syntax safety | FixEvaluator | Patch Validity, Safety, Syntax |
| `verification` | End-to-end fix, test rerun, and security rescan | VerificationEvaluator | Verification Rate, Clean Rescan |
| `ai_quality` | Hallucination detection, citation accuracy, honesty | CitationEvaluator / AnswerEvaluator | Hallucinated Files, Citation Validity |
| `performance` | Cold-start vs warm cache latency, blast radius computation | BenchmarkCaseRunner | Layer Latencies, P95/P99 |

## 3. Benchmark Execution Lifecycle

Every benchmark run proceeds through strict phases:
```text
1. Filter & Case Selection: Match categories, tags, difficulties, and project scope.
2. Anti-Circularity Check: Verify ground truth is independent and deeply frozen.
3. Case Runner Loop:
   a. Apply per-case timeout (15s default).
   b. Profile layered latencies (Gateway, Retrieval, LLM, Validation).
   c. Execute domain evaluator.
   d. Validate evidence citations against actual project files.
   e. Record pass/fail and failure diagnostic if failed.
4. Aggregate Scoring: Compute category scores, precision, recall, Hit@K, MRR.
5. Hash Computation: Generate canonical SHA-256 configuration and dataset hashes.
6. Regression Analysis: Compare against baseline using Regression Engine 2.0.
7. Telemetry & Artifact Persistence: Redact secrets and store immutable run records.
```

---

## 4. Benchmark Result Contract & Diagnostics

Failed cases produce structured `FailureDiagnostic` records:
- `failureType`: `"VULNERABILITY_NOT_FOUND"`, `"FALSE_POSITIVE"`, `"HALLUCINATED_CITATION"`, `"PATCH_APPLICATION_FAILED"`, `"TIMEOUT_EXCEEDED"`.
- `expectedSummary`: Independent ground truth requirement.
- `actualSummary`: Observed behavior.
- `remediationHint`: Practical guidance for correcting prompt templates, context limits, or retrieval queries.
